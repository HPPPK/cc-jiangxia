# 浏览器信息检索与多源取证

## 角色边界

本 Skill 是“如何用浏览器做公开信息检索”的方法，不是新的搜索 API、爬虫服务或绕过工具。

- BrowserResearch / Playwright 是底层执行器：打开公开网页、在可见搜索页面中输入关键词、读取渲染文字与链接、按需保存截图，并返回实际错误。
- 本 Skill 决定先查哪个字段、用什么查询词、从哪个入口发现候选链接、哪些链接必须再打开、怎样记录来源、遇到限制时如何合规处理。
- 模型已有知识和搜索摘要只能帮助规划，不是报告事实。
- 只使用当前会话真实存在的工具。本 Skill 不授予 WebSearch、WebFetch、登录、验证码处理、代理/VPN、下载、写文件或任何绕过访问限制的权限。

## 核心原则：发现与取证分开

搜索页、搜索摘要、排序、热榜和 AI 摘要只用于发现候选链接，不能直接作为市场、用户、竞品或渠道结论的证据。

官网页、定价页、帮助页、应用商店页、具体文章、帖子、视频、评论和公开数据页，必须由 BrowserResearch 单独打开后，才可作为报告证据。

如果最终报告使用了一个页面的信息，必须保留实际 URL、标题、访问日期、对应字段和证据状态。只有候选 URL 而未成功打开时，只能称为“候选链接”或“公开页面线索”。

## 研究前：字段级检索计划

开始网页研究前，对每个待验证字段建立一行计划：

待验证字段 | 需要证明或反证的内容 | 查询词 | 候选来源类别 | 检索入口 | 目标具体页 | 成功标准 | 失败后的替代路径

示例一（不绑定具体产品）：
竞品价格与免费边界 | 是否有公开价格、套餐差异和升级条件 | 产品名 pricing / 产品名 价格 | 官网、订阅页、应用商店 | 官网根页或 Bing | pricing / FAQ 具体页 | 页面直接写明金额或套餐 | 官方帮助中心、商店内购页、更新公告

示例二：
用户痛点 | 用户在什么任务下认为现有方案不够 | 任务词 + 问题词 + 替代方案 | 公开社区、应用评价、内容评论、问答 | Bing / Google / Baidu / 平台站内入口 | 单条帖子、具体评价或评论页 | 有可读的任务、痛点或替代方案表达 | 换关键词、换独立平台、记录证据缺口

不要预设某个产品、竞品、国家、语言、平台或社区一定适用；根据本轮产品方向、市场范围、用户材料和字段需要选择入口。

## 多入口检索策略

### 1. Bing：通用公开网页发现

当只知道产品名、竞品名、任务词或研究问题时，用 BrowserResearch 的**搜索模式**发现官网、文章、应用商店、论坛或数据页的真实链接。商业化专家的每次搜索发现都明确写出引擎，避免“提示词说百度、实际跑 Bing”的误记：

```text
BrowserResearch({
  search_query: "产品名 pricing",
  search_engine: "bing",
  task: "为竞品价格字段发现官方价格或购买页"
})
```

Bing 是通用基线；它返回的搜索页只用于发现候选链接。筛选相关真实链接后，必须再用 `BrowserResearch.url` 分别打开具体页面。

### 2. Google：海外、英文、国际资料补充

当研究范围包含海外、英文、国际产品资料或国际讨论，并且 Bing 未找到官方候选、结果无关或访问受限时，使用同一个搜索模式，**不要手工拼 Google 搜索 URL 再当作普通页面打开**：

```text
BrowserResearch({
  search_query: "product name pricing official",
  search_engine: "google",
  market: "US",
  locale: "en-US",
  task: "为海外竞品价格字段发现官方页面"
})
```

`market` 与 `locale` 只有用户或研究范围已经明确时才传。Google 可能因地区、同意页、验证码或访问策略受限；若受限，工具回执应记录 `engine=google` 和真实失败 URL，然后改用 Bing、官网、应用商店、GitHub、公开平台入口或用户材料。不得绕过限制。

### 3. Baidu：中文网页、中文社区与国内资料补充

当研究范围包含中文用户、中文互联网内容或中国市场时，也用搜索模式明确选择 Baidu：

```text
BrowserResearch({
  search_query: "产品名 用户评价 使用场景",
  search_engine: "baidu",
  task: "为中文用户需求字段发现可逐页核验的具体内容"
})
```

Baidu 搜索页的摘要、热榜和排序不等于真实需求或市场规模。必须从结果中找到具体官网、文章、帖子、问答、视频、商店或公开数据页，并逐页打开。

### 4. 360 搜索：中文市场的公开降级入口

当本轮范围包含中国大陆公开网页，且 Baidu 出现 CAPTCHA、登录、访问受限或结果质量明显不足时，用搜索模式改选 360：

```text
BrowserResearch({
  search_query: "产品名 用户评价 使用场景",
  search_engine: "360",
  task: "在 Baidu 受限后，为同一字段发现独立的公开候选链接"
})
```

360 同样只用于发现候选链接和记录可见广告/自然结果快照。若最终报告使用了某个关键词快照观察，必须把该关键词对应的**真实 final URL**单独放进来源表；一条 360 搜索页不能代替多个不同关键词方向的来源记录。

### 5. 已知站点与已打开页面的真实链接

- 已有官网、价格页、帮助中心、应用商店、GitHub、行业资料或用户提供链接时，直接用 BrowserResearch.url 打开，不需要先走搜索页。
- 从已打开页面返回的真实链接中，只扩展与当前字段有关的页面，形成“来源 A 发现 B → 实际打开 B”的来源图谱。
- 对社区、社媒、视频和内容平台，优先进入具体内容页；根页、话题页、分类页和搜索页通常只承担发现作用。

## 无需 API Key 的公共候选入口

本专家不依赖 Google Grounding、Gemini、Tavily、Brave、Serper 或其他付费/Key 型搜索 API。不要要求用户配置搜索 Key，也不要把模型记忆、搜索摘要或 API 返回摘要写成报告事实。

当常规搜索入口没有发现足够候选页、或某个入口受限时，按字段需要选择下列公开、低频、零 Key 入口。它们只帮助发现候选 URL；从这些入口得到的每一个候选仍须用 BrowserResearch.url 单独打开后，才可进入最终来源表。

入口 | 适用字段 | BrowserResearch 使用方式 | 边界
--- | --- | --- | ---
官方网站、帮助中心、价格页、更新日志、站点地图、RSS | 功能、版本、价格、免费边界、官方公告 | 已知 URL 或由已打开页面的真实链接直接用 url 打开 | 一手产品事实；不能单独证明外部用户需求或渠道效果
GitHub 公开仓库、Release、Issues、项目主页 | 开发者工具、开源替代、版本节奏、安装方式、公开维护信号 | 先通过 Bing、已知组织页或低频 GitHub 公开搜索页发现仓库，再逐页打开仓库、Release 或具体 Issue | Stars、Issue 数或提交数不是市场规模、用户频率或付费意愿
平台定向 Bing / 360 搜索与对应具体页 | 应用商店、公开社区、社媒、视频、评测或问答的候选发现 | 以 site:平台域名 + 产品/任务/痛点词进行浏览器 search_query，再打开具体条目 | 搜索页只发现链接；必须逐页打开，且平台访问受限时不绕过
Hacker News Algolia 与 Stack Exchange 公开搜索响应 | 开发者/知识工作者产品的公开讨论、技术痛点、替代方案线索 | 仅在对象匹配时，低频读取公开搜索响应，从其中提取候选链接后再打开原帖或外链 | 仅适用于相关技术人群；JSON 响应、命中数和单帖都不能代表整体市场或用户比例
公开应用商店、公开评测、问答、社区或内容具体页 | 评价、任务、痛点、替代方案、内容供给线索 | 由搜索结果、官方跳转或已打开页面的链接发现后，用 url 打开具体条目 | 根页、话题页、分类页和搜索页通常只发现链接，不直接证明用户结论

用于零 Key 候选发现的公开 URL 形态示例（只按字段匹配时使用，且结果仅作候选）：

- 平台定向候选：用 BrowserResearch.search_query 传入 site:目标平台域名 + 产品/任务/痛点词；从真实结果中打开具体条目。
- Hacker News： https://hn.algolia.com/api/v1/search?query=<编码后的查询>&tags=story&hitsPerPage=5
- Stack Exchange： https://api.stackexchange.com/2.3/search/advanced?order=desc&sort=relevance&q=<编码后的查询>&site=stackoverflow&pagesize=5
- GitHub：优先用 BrowserResearch 的搜索入口或已知组织/仓库页；若使用公开仓库搜索页，只取其中返回的真实仓库链接继续逐页打开。

使用这些入口时：

1. 按字段匹配，不要为了来源多而机械全跑。例如开发者工具优先 GitHub、Hacker News 或 Stack Exchange；应用软件的商店或公开社区信号优先平台定向检索；产品事实优先官网与官方文档。
2. 每个接口或目录至多做一次低频、相关的候选发现。若返回 403、429、登录、CAPTCHA、JSON 无法读取或内容无关，记录真实限制后换同字段的公开入口，不要重试轰击、换代理或绕过。
3. 候选响应不是证据。必须记录入口或父页面、候选 URL、实际打开 URL、页面结果；最终报告只引用实际打开且与主张匹配的具体页。若公开入口返回 JSON 而 links 为空，只能从 BrowserResearch 返回的正文中提取已经真实出现的 URL 或字段：Hacker News 可将真实出现的 objectID 组成 https://news.ycombinator.com/item?id=<objectID> 后再打开；Stack Exchange 只使用响应中真实出现的 link。不得编造帖子、链接或数据。
4. 入口没有替代品时如实留缺口。例如没有公开社区、商店或 GitHub 资料，不能用别的产品的页面凑成多源，也不能声称未找到就代表不存在。
## 高影响字段的入口切换

不要为了“覆盖搜索引擎”而机械把所有入口都跑一遍；但也不能只因一个入口失败就收口。对会影响立项、竞品价格、用户需求或渠道结论的字段：

1. 先选择与市场和语言匹配的首个入口：通用发现可先试 Bing；中国公开网页可补 Baidu 或 360；海外/英文资料可补 Google。搜索引擎只是候选入口，不是必经依赖。若 Bing/Google/Baidu 任一入口出现 access_limited、CAPTCHA、无关结果或无可核验链接，不重复轰击；按字段切换到 360、官网/文档、平台定向搜索、GitHub、Hacker News、Stack Exchange 或用户提供材料。对本专家的每个 `search_query`，显式传 `search_engine`。
2. 若首个入口返回 `search_irrelevant`、`access_limited`、`target_unavailable`，或未发现可逐页核验的候选链接，必须做一次相关的独立替代：
   - 海外/英文的直接竞品资料：`search_engine: "google"`，或其官方商店 / GitHub / 文档入口；
   - 中文/大陆资料：`search_engine: "baidu"`；若 Baidu CAPTCHA 或受限，再尝试 `search_engine: "360"`；
   - 已知官方链接：直接转向官方价格页、帮助中心、应用商店、GitHub Release 或官方公告。
3. 每次切换都保留“首入口 → 为什么切换 → 替代入口 → 结果”的台账。每次尝试记录查询词或 URL、**工具回执中的实际 engine**、目标字段、真实 final URL、结果（成功/无关/受限/运行时阻断）、访问日期、下一步。不得把 Bing 回执写成 Baidu / Google / 360 搜索结果。若替代入口仍无证据，写“证据缺口”，而不是“网上没有信息”。

## 运行时浏览台账与跨子代理对账

Playwright 是浏览器的“手和眼睛”；本 Skill 才是“先去哪找、怎样判断结果、失败后怎样合法换入口、如何留痕”的方法。子代理完成时，系统会根据**真实 `BrowserResearch` 工具调用及其原始结果**生成 `<browser-research-audit>`，主代理和复核子代理必须优先相信这份台账，不能以子代理自然语言中的“我查到”“我打不开”取代工具回执。

台账状态 | 含义 | 正确处理
--- | --- | ---
`opened` | 该次调用至少实际打开了一个页面 | 只将该页面中与字段直接有关的内容作为候选证据；仍要记录证据边界。
`search_irrelevant` | 搜索页加载了，但自然结果与查询对象无实质关联 | 不把这些链接或摘要用作来源；收紧对象词/任务词，或换合规入口。
`access_limited` | CAPTCHA、登录、robots、403/429、地区或其他访问控制 | 记录 URL/查询词和限制；换公开来源，不绕过限制。
`target_unavailable` | 某个 URL 是 404、错误 App Store 页面或当前不可用目标页 | 只说明**这个候选 URL**无效；可查官方备用网址或真实页面链接，绝不外推成“产品不存在/整体不可访问”。
`failed` / `pending` | 浏览器调用失败、运行时出错或没有配对结果 | 标为执行/证据缺口；运行时故障按停止规则熔断，单页故障则做有限、相关的替代尝试。

跨子代理出现冲突时，按以下顺序处理：

1. 同一事实优先采用正确产品页、官网/帮助中心/定价页等**实际已打开**的一手页面。
2. 一条成功打开的正确页面，高于另一条错误候选 URL 的失败；在台账写“此前候选 URL 失效/不对应”，不写“产品整体无法访问”。
3. 搜索结果页面、无关结果、搜索摘要、单个失败 URL 只能说明检索过程，不能单独支持市场、用户、价格或可用性结论。
4. 复核子代理必须逐条读取 `<browser-research-audit>`；若正文主张与台账冲突，打回为“待验证/修正”，不得因文笔流畅而放行。

## 查询词构造

每个字段至少准备“对象词 + 任务或事实词 + 证据词”三部分；按当前范围选择中文、英文或双语，不要机械地所有语言都搜。

研究目的 | 查询词结构示例 | 目标页面
产品或竞品事实 | 产品名 + pricing / 价格 / 功能 / 更新日志 | 官网、订阅页、帮助页、更新日志
用户痛点 | 任务词 + 痛点词 + 求助 / 评价 / 替代 / why | 具体讨论、问答、评价、评论
渠道线索 | 任务词 + 教程 / 测评 / 推荐 / 下载 / 插件 | 具体文章、视频、分发页、公开讨论
市场与趋势 | 品类词 + report / statistics / trend / 行业报告 / 统计 | 原始发布者页面、公共数据页、报告说明页

根据页面结果补充同义词、替代方案、平台名、功能名或用户任务词；不要把搜索结果数量、排名或内容数量直接推成需求规模、用户频次或付费意愿。

## 单页取证与来源台账

每次成功或失败的访问都记录最少信息：
字段 | 发现入口 | 查询词或父页面 | 实际打开 URL | 页面标题 | 页面类型 | 访问日期 | 观察到的原文或数据 | 支持什么 | 不能支持什么 | 状态 | 限制

状态只能从实际结果中选用：
- 已打开-支持：页面直接支持当前字段。
- 已打开-部分支持：只支持部分表述，剩余部分必须降级。
- 已打开-矛盾：页面与既有说法冲突，保留冲突并交给复核。
- 已打开-无关或无结果：页面可访问但没有目标证据。
- 访问受限：登录、CAPTCHA、robots、403、429、地区限制、付费墙等。
- 运行时阻断：Node、Playwright、Chromium、桥接进程或本机路径故障。

报告中每个被采用的结论都要对应到已打开 URL；如果网页只用于发现来源、没有被报告使用，可以只留在访问台账。

## 直接竞品补证路径

“直接竞品”必须随本次产品方向动态发现，不能预先固定品牌。每个被写入直接竞品或价格对比表的产品，优先按以下顺序补证：

官网首页 → 官方 pricing / buy / FAQ → 官方应用商店页 → 官方 GitHub / Release / 文档 → 官方博客或更新公告。

- 官网首页受限时，继续尝试同一产品的官方商店、GitHub、文档或发布页；不要用宽泛替代品的价格填补它的价格空白。
- 第三方页面只能作为“发现线索”或明确标为第三方观察，不能替代官方价格事实。
- 多次合理尝试后仍未取得官方证据时，竞品可保留在“直接竞品 / 替代方案”表中，但价格、平台或功能字段必须写“未取得，需一手验证”；来源表需保留受限 URL 和限制原因。
- 云协作、通用笔记、办公套件等宽泛替代品必须在表中标为“替代方案 / 生态替代”，不得伪装成已核验的直接 Markdown 竞品。

## 最终报告来源闭环（强制）

在写入 `report-fields.json` 前，主代理必须从三个研究子代理和复核结果整理“主张 → 已打开 URL → [n] 来源编号”的最终映射：

1. `SOURCE_ROWS` 中必须包含每一条最终报告实际使用的页面或搜索快照 URL，并说明支持什么、不能支持什么、访问日期和来源类型。
2. 一条具体的搜索关键词观察对应一条具体 SERP URL。若报告写“6 个关键词方向”，来源表必须有这 6 条 URL，或把正文改为只描述已留痕的方向；不得用一条搜索页代替多条关键词快照。
3. 数字、价格、播放量、内容数量、广告位、日期等必须各自能定位到直接来源行；三篇文章不能替代标签页的内容总量，一张截图不能替代不同平台的数据。
4. `access_limited`、`target_unavailable`、无关结果等可以进入来源表，但只能支持“本次未取得 / 访问受限”的说明，不能支撑正向市场或竞品结论。
5. 来源表可以较长；宁可保留简洁的一行一 URL，也不要将不同 URL 压缩成不可复核的“综合搜索观察”。

## 合规容错与停止规则

| 情况 | 正确处理 |
| --- | --- |
| 页面正常但无目标信息 | 查看真实站内链接；或用不同字段词到另一入口检索。 |
| 页面无关、搜索结果质量低 | 调整对象词、任务词、证据词，或换 Bing、Google、Baidu、站内入口、官方分发页等同类入口。 |
| Google、Baidu 或 Bing 单一入口失败 | 记录入口、查询词、错误和日期；换其他公开入口，不把单一搜索引擎失败说成“网上没有信息”。 |
| 403、429、CAPTCHA、robots、登录、付费墙、地区限制 | 保留限制和 URL；换合法公开来源。不得登录、提交验证码、切换代理/VPN、伪装真人或绕过反爬。 |
| ERR_CONNECTION_CLOSED、页面崩溃或链接失效 | 可尝试一次与字段等价的官方备用网址、帮助中心、应用商店、GitHub、原始发布者或独立平台；不要重复轰击同一失败页。 |
| Node、Playwright、Chromium、浏览器桥接或 EISDIR 故障 | 立即停止本轮网页研究并标为“运行时阻断”；不要不断换关键词、URL 或搜索入口，也不要假装是站点限制。 |
| 多轮合理尝试仍无关键证据 | 记录已尝试入口与缺口；使用 AskUserQuestion，让用户选择提供替代链接、截图或内部资料、接受证据缺口，或明确同意对已失败 URL 进行一次 WebFetch 降级。 |

只有用户在本轮明确选择 WebFetch 降级时，才能对同一已记录失败 URL 使用一次 WebFetch。没有此选择时，不得把 WebFetch 当作浏览器或搜索工具的替代品。

## 子代理交付物

研究子代理交付时必须提供：
1. 字段级检索计划：哪些字段已查、仍待查、为何选择对应入口。
2. 候选与访问台账：包括成功、无关、受限和运行时阻断，不静默丢弃失败。
3. 主张—来源映射：每项结论对应哪个已打开 URL，以及其证据边界。
4. 可继续的候选路径：下一步应打开的具体链接或仍缺的用户材料，而不是泛泛地说“继续搜索”。
5. Skill 使用说明：只声明本次实际执行过的方法和工具结果；阅读本 Skill 不等于已取得外部证据。

## 完成前自查

- 是否把搜索页、摘要、排序、热榜或模型记忆误写成了报告事实？
- 是否把每个最终使用的网页结论都回到了具体已打开页面？
- 是否清楚区分“已观察、公开页面线索、推断、待验证、访问受限、运行时阻断”？
- 是否在单一入口失败后尝试了合理的独立公开入口，而没有绕过限制或无限重试？
- 是否保留了 URL、日期、页面标题、字段和限制，使复核子代理能逐项检查？
- 报告中的每个搜索关键词方向、外部数字和直接竞品价格，是否都有可点击的单独来源行，而不是用同类页面或综合描述替代？
- 对每个直接竞品，是否已走完官网 → 价格页 → 官方商店 / GitHub / 文档的合理补证路径，或如实标为未取得？
